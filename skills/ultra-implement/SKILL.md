---
name: ultra-implement
description: Implement every sub-issue of a parent issue unattended, as one combined PR when they build one thing, or one PR each when they are separate work. Sub-issues run in dependency order, and the ones whose predecessors are ready run in parallel. Each PR gets tests, browser checks and screenshots where they fit, and a three-lens review. Run it by typing /ultra-implement with the parent issue.
license: MIT
argument-hint: '<parent issue link or reference>'
disable-model-invocation: true
---

`$ARGUMENTS` holds the parent issue. If it is empty, ask for it and stop.

Read `workflow.js` in this skill's directory. Call the Workflow tool with its full contents as `script` and `args` set to `{ "parent": "<the parent issue>" }`. The tool refuses a `scriptPath` outside the working directory. Typing this skill's command is the user's opt-in to the workflow.

The workflow needs a GitHub remote and the gh CLI. It holds no other facts about a repo: it finds out the CI checks, the review bot, the type check, the scripts, the browser setup, the branch names and how to open a PR from the repo and its project instructions at the start of each run.

The workflow:

1. Reads the parent issue and the sub-issues once, and passes their descriptions to every later agent, so no agent reads the tracker for them again. The parent's description is the spec for every sub-issue. At the same time, a preflight checks that the dev server and the browser login work, finds test data, and starts one before server from the default branch, which every agent uses for its before screenshots and which is stopped at the end of the run. When they do not work, the run stops before any sub-issue starts. A third agent finds out what CI does with a PR: which checks run and how to reproduce them locally, the type check command, if any, whether a review bot runs and when (when a PR opens, after each push, or only when asked), and which human approvals a merge needs. Implementers and finishers run the CI checks that their change can break before they push. The addresser waits for a bot only when one reviews by itself, never asks one for a review, and never waits for a human. It pushes once per round of fixes, so no CI run or bot review is spent on half the fixes. The plan also finds out if the spec is a refactor or a migration, where existing screens must look and behave as before (preserve mode).
2. Orders the open sub-issues by their dependency links. It skips the ones that need a person (a release, a sign-off, an open decision) and the ones in a dependency cycle. It also picks the delivery. `shared` lands every sub-issue on one shared branch, with no PR of its own, and opens one PR from that branch to the default branch: for sub-issues that build one thing, a spec or project instructions that ask for one branch or one PR, or slices that must not ship alone. It creates the shared branch from the default branch and names it for the whole change, not for its first sub-issue. `separate` gives each sub-issue its own PR to the default branch, for separate work that ships alone. When the shared branch cannot be created, the run stops before any sub-issue starts.
3. Starts each sub-issue when its predecessors are ready, in its own worktree, on a branch named for that sub-issue. With `separate`, the branch and the PR base are the predecessor's branch, or else the default branch. With `shared`, the branch starts from the shared branch, after its predecessors have landed on it.
4. With `shared`, each implementer tests its sub-issue, merges it into the shared branch and pushes, with no PR, and moves the sub-issue to the stage that the project instructions give a landed slice. When every sub-issue has landed, the review, finish and address steps below run once, on the shared branch. The finisher opens its PR to the default branch, and the addresser moves the parent to review.
5. With `separate`, per sub-issue: implement with tests first and browser checks where the change is visible, and push the branch with no PR. Then correctness, design and spec reviewers read the branch in parallel. Then a finisher fixes the findings, re-checks only what its fixes change, takes the screenshots, runs the type check once as its last check, and only then opens the PR, so that CI and a review bot that runs when a PR opens see the finished code. Then an addresser that waits for CI and the CI review, addresses the PR with the address-pr skill, pushes the fixes once, and moves the issue to review without waiting for the CI run that the push starts. The sub-issues after it start when the finisher is done, while the addresser runs.
6. Stops a sub-issue that needs a change outside the repo, and blocks the sub-issues after it. A sub-issue whose only open checks need a person to set up returns needs_person and does not block the ones after it.
7. In preserve mode, the before screenshots come from the default branch, and each difference on an existing screen that the spec does not name is fixed. When all sub-issues have finished, one agent merges every ready PR branch, or the shared branch, (never pushed) and compares the touched screens with the default branch in a browser. It returns the differences, each with its PR.

Before a resume of a run, remove that run's worktrees and local branches that have no changes, since old worktree paths block the new ones.

For an unattended run, start the session in auto permission mode, then send it to the background.

When the workflow returns with a blocked preflight or a blocked shared branch, tell the user what to fix, such as logging in again or creating the branch, and to run the command again. Otherwise state the delivery and its reason. With `shared`, give the combined PR link, its status and the parent's stage, and then a table with one row per sub-issue: the issue, the status (landed, or why not) and the tracker stage. With `separate`, give a table with one row per sub-issue: the issue, the PR link, the status, and the tracker stage. Add the reason for each skipped, blocked, needs_person or failed one. Then list what the user must do next: the blocked backend changes, the checks that need a person, the skipped sub-issues, and the PRs to review, with the human approvals that `ci.humanReview` says a merge needs. When PRs stack (a PR's base is another sub-issue's branch), give the merge order as a numbered list, bottom of the stack first. When the default branch moved during the run and a stack exists, merge it through the stack bottom-up before you report the order, or list that as a next step. When the preserve check ran, give its differences and their PRs.
