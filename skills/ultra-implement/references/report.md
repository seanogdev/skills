# Report

When the workflow returns with a blocked preflight or a blocked shared branch, tell the user what to fix, such as logging in again or creating the branch, and to run the command again. Otherwise state the delivery and its reason. With `shared`, give the combined PR link, its status and the parent's stage, and then a table with one row per sub-issue: the issue, the status (landed, or why not) and the tracker stage. With `separate`, give a table with one row per sub-issue: the issue, the PR link, the status, and the tracker stage. Add the reason for each skipped, blocked, needs_person or failed one. Then list what the user must do next: the blocked backend changes, the checks that need a person, the skipped sub-issues, and the PRs to review, with the human approvals that `ci.humanReview` says a merge needs. When PRs stack (a PR's base is another sub-issue's branch), give the merge order as a numbered list, bottom of the stack first. When the default branch moved during the run and a stack exists, merge it through the stack bottom-up before you report the order, or list that as a next step. When the preserve check ran, give its differences and their PRs.
