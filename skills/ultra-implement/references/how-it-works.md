# How the workflow works

The workflow needs a GitHub remote and the gh CLI. It holds no other facts about a repo: it finds out the CI checks, the review bot, the type check, the scripts, the browser setup, the branch names and how to open a PR from the repo and its project instructions at the start of each run.

The workflow:

1. Reads the parent issue and the sub-issues once. The parent's description is the spec for every sub-issue. Every later agent gets the acceptance criteria of its own sub-issues, quoted as written, and the few rules of the spec that bind every sub-issue, such as the seams to test at, the flags and what is out of scope. It reads the full spec or a full description from the tracker only when those leave a question open. Only the implementer, which reads its sub-issue's description first, the spec reviewer, which checks the user stories of the spec too, and the preserve check read them up front. A sub-issue with no acceptance criteria points its agents at its description and the spec. At the same time, a preflight checks that the dev server and the browser login work, finds test data for each sub-issue that changes something visible, which reaches only that sub-issue's agents, and starts one before server from the default branch, which every agent uses for its before screenshots and which is stopped at the end of the run. When they do not work, the run stops before any sub-issue starts. A third agent finds out what CI does with a PR: which checks run and how to reproduce them locally, the type check command, if any, whether a review bot runs and when (when a PR opens, after each push, or only when asked), and which human approvals a merge needs. Implementers and finishers run the CI checks that their change can break before they push. The addresser waits for a bot only when one reviews by itself, never asks one for a review, and never waits for a human. It pushes once per round of fixes, so no CI run or bot review is spent on half the fixes. The plan also finds out if the spec is a refactor or a migration, where existing screens must look and behave as before (preserve mode).
2. Orders the open sub-issues by their dependency links. It skips the ones that need a person (a release, a sign-off, an open decision) and the ones in a dependency cycle. It also picks the delivery. `shared` lands every sub-issue on one shared branch, with no PR of its own, and opens one PR from that branch to the default branch: for sub-issues that build one thing, a spec or project instructions that ask for one branch or one PR, or slices that must not ship alone. It creates the shared branch from the default branch and names it for the whole change, not for its first sub-issue. `separate` gives each sub-issue its own PR to the default branch, for separate work that ships alone. When the shared branch cannot be created, the run stops before any sub-issue starts.
3. Starts each sub-issue when its predecessors are ready, in its own worktree, on a branch named for that sub-issue. With `separate`, the branch and the PR base are the predecessor's branch, or else the default branch. With `shared`, the branch starts from the shared branch, after its predecessors have landed on it.
4. With `shared`, each implementer tests its sub-issue, merges it into the shared branch and pushes, with no PR, and moves the sub-issue to the stage that the project instructions give a landed slice. When every sub-issue has landed, the review, finish and address steps below run once, on the shared branch. The finisher opens its PR to the default branch, and the addresser moves the parent to review.
5. With `separate`, per sub-issue: implement with tests first and browser checks where the change is visible, and push the branch with no PR. Then correctness, design and spec reviewers read the branch in parallel. Then a finisher fixes the findings, re-checks only what its fixes change, takes the screenshots, runs the type check once as its last check, and only then opens the PR, so that CI and a review bot that runs when a PR opens see the finished code. Then an addresser that waits for CI and the CI review, addresses the PR with the address-pr skill, pushes the fixes once, and moves the issue to review without waiting for the CI run that the push starts. The sub-issues after it start when the finisher is done, while the addresser runs. The finisher and the addresser reject a finding or a comment that asks for more than the sub-issue and the rules ask for, unless it is a bug that the change brings in, so that review does not widen the PR.
6. Stops a sub-issue that needs a change outside the repo, and blocks the sub-issues after it. A sub-issue whose only open checks need a person to set up returns needs_person and does not block the ones after it.
7. In preserve mode, the before screenshots come from the default branch, and each difference on an existing screen that the spec does not name is fixed. When all sub-issues have finished, one agent merges every ready PR branch, or the shared branch, (never pushed) and compares the touched screens with the default branch in a browser. It returns the differences, each with its PR.
8. When at least one PR is open, a completeness check reads the spec and the diff of each PR, read only and with none of the implementers' notes, and returns each user story or requirement that no PR delivers, or delivers only in part, as gaps. It leaves out what only a skipped, blocked or failed sub-issue covers, since the report lists those already. It runs at the same time as the preserve check.
